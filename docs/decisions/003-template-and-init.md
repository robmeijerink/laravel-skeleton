# 003: Template Plus `task init`, No Laravel Code in the Skeleton

## Context
The skeleton must install the newest Laravel, starter kits and packages five years from now, with almost no maintenance. A committed Laravel app would be outdated the day after it is committed, and every year of upgrades would land on the skeleton's maintainer.

## Decision
_Template-only files: `.skeleton/`, `.github/workflows/skeleton-smoke.yml`, `.github/workflows/release.yml` and `CHANGELOG.md` exist only in the template; `init` deletes them, so a generated project keeps this record as history._

The repository contains **no Laravel code**: only the container setup, the agent sandbox, Taskfile, CI and `.skeleton/`. After "Use this template" on GitHub, `task init` runs the official `laravel/installer` (always the newest release) inside the dev container, in a temporary folder, because the installer refuses a non-empty directory and `--force` on the current one. The result is merged into the repo with `rsync --ignore-existing`, so skeleton files always win; `.gitignore` is merged line by line. Afterwards `init` deletes `.skeleton/`, the `init` task, the smoke-test and release workflows and the changelog.

* **Stacks:** the official React, Vue and Livewire kits, their blank variants (`--no-auth`, the minimal Inertia setup), plain Blade with Vite, and two own SPA stubs (React, Vue). The kits are maintained by Laravel; only the SPA stubs (`.skeleton/stubs/`) are ours, and they stay as small as possible because they are the part that ages.
* **Add-ons** (Filament, Mailpit, Redis) are separate scripts in `.skeleton/addons/` that run after the base install. Compose services for add-ons are marked blocks that `init` keeps or drops.
* **Wizard and flags:** `task init` asks with gum; `task init -- --vue --no-auth --filament` skips the questions, so it is reproducible and usable by an agent and CI.
* **Boost is not installed:** it writes its own `AGENTS.md`/MCP config and expects PHP on the host; `AGENTS.md` here is the source of truth.

## Keeping the Template Honest
Nothing is pinned except the PHP minor ([004](004-stack-choices.md)), so the template can break without a commit (an installer flag is renamed, a kit changes its Vite config). `.github/workflows/skeleton-smoke.yml` runs `task init` for every variant and then `task check`, the project's CI command (`composer qa:ci`) and a production build, on every push to `main`, on every pull request and weekly. A failing run is the signal that `.skeleton/` needs a fix; `init` fails loudly (for example when it cannot patch the Vite config or `phpunit.xml`) instead of producing a half-configured project.

## Upstream Quirks `init` Works Around
Found while building the skeleton (2026-11); each one is a place the smoke test will show first if upstream changes:
* **The React kit's `install:features` hook calls `npm`** when it finds no lock file, and the image has no Node. `LARAVEL_INSTALLER_NO_NODE=1` makes the hook skip it; the installer then installs with Bun (`--bun`). If a kit stops honouring the flag, `init` fails with `npm: not found`.
* **`node_modules/` from the temporary folder is not merged** (native binaries and paths point at `/tmp`), so `init` runs `pun install` and `bun install` in the repo.
* **The kits ship their own `phpstan.neon` (level 7), `pint.json` and Composer scripts.** `init` removes them with Pint, Larastan and Rector, writes its own `pun.toml` for every stack, and points the kits' Composer scripts that call the removed tools (`lint`, `lint:check`, `types:check`, referenced by `composer test`) at the matching Pun command ([005](005-pun.md)).
* **The kits' `vite.config.ts` already has a `server:` block.** A second key would silently override the first, so `patch-vite.sh` extends the existing block (`host: '0.0.0.0'`, `hmr.host: 'localhost'`) and falls back to adding one.
* **`api.github.com` returned HTTP 504 for unauthenticated zipball downloads** in most Composer runs; `composer config --global use-github-api false` (in both images) downloads from github.com instead. `init` also retries Composer three times.
* **The kits' frontend formatter formats the whole repository.** `bun run check:fix` (Oxfmt) rewrote the template's Markdown, JSON and YAML, and in the agent sandbox, where `.devcontainer/`, `.claude/` and the Taskfile are read-only, it would fail. `.prettierignore` (which Oxfmt honours; verified by removing it and watching the check fail) lists the template's own files.
* **Inertia renders server-side through the Vite dev server while `task dev` runs** (`public/hot` exists). In tests that is a real HTTP request to `/__inertia_ssr`, which Essentials blocks, so every Inertia page test failed with a 500, but only while the dev server was running. `init` makes `inertia.ssr.enabled` read `INERTIA_SSR_ENABLED` and sets it to `false` in `phpunit.xml`; it fails loudly if the kit's config no longer has the line it expects.
* **Laravel's own `resources/js/app.js` is empty** (Blade, Livewire): an entry point for Vite. Oxlint's `unicorn/no-empty-file` fails on it under `--deny-warnings`, so `.oxlintrc.json` switches off that one rule; every other default rule stays on.
* **TypeScript 7 (native) and `vue-tsc`:** the latest `typescript` is 7.x, which `vue-tsc` does not support yet. The Vue SPA stub installs `typescript@^5`, like Laravel's own kits; the React SPA stub uses the latest.
* **Code coverage must be 100, for new code too.** `init` starts Postgres (it used to run without), runs the tests once with a Clover report, and `.skeleton/ignore-uncovered.php` excludes every statement the kit's tests don't reach: `// @codeCoverageIgnore` on a single line, one `@codeCoverageIgnoreStart`/`End` pair around consecutive lines (a first version marked every line of a multi-line statement separately, which was noisy). In practice these are production-only branches, such as the strict password rules in `AppServiceProvider`. Coverage is line coverage: pcov does not measure branches, and Xdebug, which does, slows every test run considerably. A file that would no longer parse after marking is restored; if the total is still below 100, `init` writes the measured value as the minimum and prints a `NOTE`.
* **`sed -i` leaves files at 0600 on macOS bind mounts** (Colima), so `config/inertia.php`, `composer.json` and the other files `init` edits were readable only by their owner. The production image runs as `www-data` and answered every request with a 500 (found 2026-11-24, `task build` from a Mac; CI never saw it, because Linux keeps the mode and git stores none). The build stage runs `chmod -R a+rX` before the runtime stage copies the app.
* **PAO changes Pest's output when an agent runs `task init`.** `init` reads Pest's human output to set the coverage markers; with `CLAUDECODE` (or another agent variable) set, PAO prints JSON instead, nothing was marked and type coverage started at 98% (found 2026-11-24, running `init` from Claude Code). `install.sh` exports `PAO_DISABLE=1`.
* **Type coverage must be 100, for new code too.** The React kit's PHP scored 98.2%: one closure parameter (`fn ($passkey)` in `SecurityController`) whose type comes from an Eloquent relation, which Rector cannot infer. `init` runs Rector's type-declaration set and the formatter (both through Pun), then marks what is still untyped with `// @pest-ignore-type` (the plugin reads that marker per line; `.skeleton/ignore-untyped.php` turns Pest's own report into markers) and prints each location as a `NOTE`. A lower `--min` would have let new untyped code slip through the gap, so that is only the last resort: if marking does not reach 100, `init` writes the measured value and says so. When upstream types that code, delete the marker.
