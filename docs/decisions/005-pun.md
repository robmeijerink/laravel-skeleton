# 005: Pun Replaces Pint, Rector, Larastan and Most of Composer

## Context
The quality setup used four PHP tools with four configs: Pint (`pint.json`), Rector (`rector.php`), Larastan (`phpstan.neon` and a baseline) and Composer for the packages. [Pun](https://punphp.com) (`shipfastlabs/pun`, MIT) is one Rust binary that formats like Pint, lints with Rector's sets, analyses like PHPStan with Larastan's checks, and installs Composer packages, from one `pun.toml`. It needs no PHP for the checks and is much faster. Adopted at v0.4.1 (2026-11-24).

## Decision
* **Format, lint and analyse:** `pun check --fix` in `composer qa`, `pun check` in `qa:ci`. `pun.toml` (written by `init`) keeps the previous rules exactly: the `laravel` format preset (Pint's defaults), the Rector sets `rector/dead-code`, `rector/code-quality`, `rector/type-declaration` and `rector/php-sets` (the old `rector.php`), and `phpstan/level_max` with the `laravel` and `carbon` extensions (the old `phpstan.neon` with Larastan and Carbon's extension), on the same paths. Pun's own presets (`max`, `strict`) were not used: they add checks PHPStan leaves opt-in, such as missing `@throws`.
* **Removed:** `laravel/pint`, `larastan/larastan`, `rector/rector` and `pestphp/pest-plugin-phpstan`, with `pint.json`, `phpstan.neon` and `rector.php` (the kits ship the first two). The kits' own Composer scripts that call those tools (`lint`, `lint:check`, `types:check`; `composer test` references them) now call `pun format`, `pun format --test` and `pun analyse`.
* **Baseline:** the installer's code that fails level max is recorded once in `pun-baseline.toml` (`pun analyse --generate-baseline`); new code gets no allowance. A PHPStan baseline cannot be converted.
* **Packages:** `pun install`, `require`, `update` and `remove` (`task pun -- ...`). They read and write the normal `composer.json` and `composer.lock`, so Dependabot keeps working.
* **Composer stays where Pun cannot replace it:** the Laravel installer (`laravel new` calls Composer), Composer scripts (`composer qa`, `composer run dev`; Pun has no script runner, `pun composer` only has `dump-autoload`), and Dependabot.
* **Two Pun binaries, on purpose.** The dev and production images install the latest Pun (like Composer and Bun, see [004](004-stack-choices.md)); it installs a fresh clone, whose `vendor/` is empty. The checks run the project's own Pun from `vendor/bin`, locked in `composer.lock` as `shipfastlabs/pun`. A new Pun release can add rules or change fixes, so it must arrive as a Dependabot PR that CI checks, not overnight with an image rebuild. `task pun` uses `vendor/bin/pun` once it exists.
* **Cache and links:** the package store and result cache live in the shared Composer volume (`PUN_CACHE_DIR`). `PUN_LINK_MODE=copy`, because Pun hardlinks by default: `vendor/` is on the bind mount (another filesystem), and a hardlink would let an edit in one project's `vendor/` change every other project's.
* **Production image:** Composer is gone from the build stage; `pun install --no-dev` and `pun composer dump-autoload` (byte for byte the same as Composer's) do the work.
* **Agents:** Pun has its own compact agent output and recognises the same variables as PAO (`CLAUDECODE` and others, passed through by the `app` service). PAO stays for Pest and Artisan.

## Trade-offs
* **Pre-1.0.** Pun is 0.x, released the day it was adopted. The smoke test runs it on every stack every week, and the project's own Pun only moves through a checked Dependabot PR.
* **Analysis is not yet complete.** In v0.4.1 Pun does not run every PHPStan and Larastan check (the rule reference marks them *Planned*), and its Larastan support reads macros instead of running PHP. Some bugs that Larastan would have caught can pass until Pun has the rule.
* **Type coverage still uses PHPStan.** Pest's type-coverage plugin runs PHPStan internally; Pun has no type-coverage check. PHPStan therefore stays installed as a dependency of that plugin, and the dev image keeps `memory_limit=1G`.
* **Pun's install is not Composer's.** It runs root scripts and the plugins in `config.allow-plugins`, but plugins get no package or download events, and `composer/installers` paths and VCS-only packages are not supported. If a package needs one of these, use `task composer -- ...` for it.
